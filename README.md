# Визуализация графа зависимостей Rust-пакетов (Cargo)

**Дисциплина:** Конфигурационное управление  
**Вариант:** № 2  
**Язык реализации:** Python 3  
**Формат конфигурации:** XML

## Описание проекта

Консольное приложение для анализа зависимостей пакетов Rust (Cargo) и визуализации полученного графа. Программа настраивается через XML-файл. Реализация ведётся последовательно в пять этапов.

> **Важно:** готовые менеджеры пакетов и библиотеки для получения зависимостей не используются. Сбор метаданных, разрешение SemVer-диапазонов, обход графа и вычисление порядка загрузки реализованы собственной логикой на стандартной библиотеке Python (`xml.etree.ElementTree`, `urllib.request`, `json`).

**Текущий статус:** реализованы этапы 1–4 (валидация XML, получение метаданных Cargo по HTTP, нерекурсивный DFS с фильтрацией и обработкой циклов, расчёт порядка загрузки зависимостей и сравнение с Cargo).

## Этап 1. Минимальный прототип с конфигурацией

Параметры `config.xml`:

| Параметр | Назначение |
| --- | --- |
| `package_name` | Имя анализируемого пакета (`A-Z` в тестовом режиме) |
| `repository` | URL-адрес репозитория или путь к файлу тестового репозитория |
| `test_mode` | Включение режима тестового репозитория (`true` / `false`) |
| `package_version` | Версия пакета в формате SemVer |
| `output_file` | Имя выходного файла с изображением графа (`.svg`) |
| `ascii_tree` | Включение ASCII-дерева зависимостей (`true` / `false`) |
| `filter_substring` | Подстрока для исключения пакетов из анализа |

## Этап 2. Сбор данных

Модуль `src/cargo_repo.py` запрашивает метаданные из HTTP API реестра (`https://crates.io`) или sparse-индекса (`https://index.crates.io`), отбирает обязательные зависимости (`kind = "normal"`, `optional = false`) и разрешает SemVer-ограничения (`^`, `~`, `>=`, `<=`, `=`, `*`).

## Этап 3. Основные операции

Модуль `src/dep_graph.py` строит транзитивный граф алгоритмом **DFS без рекурсии** (на явном стеке с трёхцветной разметкой состояний вершин), исключает пакеты по `filter_substring`, фиксирует обратные рёбра циклов и поддерживает файловый тестовый репозиторий (`^[A-Z]+$`).

## Этап 4. Дополнительные операции

Реализовано в модуле `src/load_order.py`:

1. **Алгоритм расчёта порядка загрузки:** используется итеративный волновой алгоритм Кана (обратная топологическая сортировка). На первой волне выбираются пакеты-листья без зависимостей, затем по мере их «загрузки» разблокируются зависящие от них пакеты вплоть до корневого пакета. Внутри одной волны пакеты упорядочиваются лексикографически.
2. **Обработка циклов:** если граф содержит циклы, строгий топологический порядок не существует. Программа явно сообщает список заблокированных циклом пакетов, перечисляет циклические рёбра, показывает узлы, доступные к загрузке до цикла, и дополнительно выводит приближённый порядок загрузки после разрыва обратных рёбер DFS.

### Сравнение результатов с реальным менеджером пакетов Cargo

#### 1. Сопоставление на пакете `serde_derive 1.0.210`

Вывод нашего приложения (`python src/main.py --config config.xml`):

```text
Порядок загрузки зависимостей (корень: serde_derive):
  1. unicode-ident (1.0.24)
  2. proc-macro2 (1.0.106)
  3. quote (1.0.45)
  4. syn (2.0.117)
  5. serde_derive (1.0.210)
```

Порядок сборки и загрузки в реальном `cargo build -v` (при добавлении `serde_derive = "=1.0.210"` в `Cargo.toml`):
1. `unicode-ident` (лист без зависимостей);
2. `proc-macro2` (зависит от `unicode-ident`);
3. `quote` (зависит от `proc-macro2`);
4. `syn` (зависит от `proc-macro2`, `unicode-ident` и `quote`);
5. `serde_derive` (корневой пакет, зависит от `proc-macro2`, `quote`, `syn`).

Для `serde_derive` последовательность загрузки и сборки полностью совпадает с Cargo.

#### 2. Причины возможных расхождений на сложных пакетах Cargo

При анализе крупных крейтов (например, `tokio`, `reqwest`, `clap`) результаты могут отличаться от `cargo tree` / `cargo fetch` по следующим причинам:

1. **Система фич (`features` и `default-features`):** Cargo автоматически активирует фичу `default`, включая связанные с ней зависимости с флагом `optional = true` (например, в `syn` зависимость `quote` объявлена опциональной и включается дефолтной фичей `printing`). Наш анализатор без вычисления графа фич учитывает только безусловно обязательные зависимости (`optional = false`).
2. **Платформозависимые зависимости (`cfg(...)` / `target`):** в метаданных `crates.io` платформенные зависимости для Windows, Linux и macOS имеют `kind = "normal"`. Реальный `cargo` отбирает только пакеты под текущую целевую ОС и архитектуру (например, `windows-sys` на Windows вместо `libc`), а наш инструмент включает все `normal`-зависимости.
3. **Сборочные зависимости (`[build-dependencies]`):** для выполнения скриптов `build.rs` менеджер Cargo дополнительно загружает и компилирует пакеты с `kind = "build"` (`cc`, `autocfg`, `pkg-config`), тогда как наш инструмент анализирует только зависимости времени выполнения (`kind = "normal"`).
4. **Глобальный резолвер версий и несколько версий одного пакета:** Cargo использует глобальный решатель ограничений с учётом MSRV и `Cargo.lock`, а также допускает одновременную загрузку двух разных SemVer-несовместимых мажорных версий одного пакета в одном графе. Наш алгоритм жадно фиксирует наибольшую подходящую версию при первом посещении пакета.
5. **Параллельная загрузка независимых ветвей:** для разветвлённого ациклического графа существует несколько корректных топологических порядков. Cargo скачивает и компилирует независимые пакеты одной волны параллельно, а наш алгоритм детерминированно сортирует узлы каждой волны по алфавиту.

## Этап 5. Визуализация (план)

- Генерация представления графа на языке диаграмм **D2**, сохранение в **SVG** (`output_file`) и режим `ascii_tree`.

## Коды ошибок приложения

| Код | Причина |
| --- | --- |
| `E01` | Файл конфигурации не найден или не читается |
| `E02` | Некорректный XML |
| `E03` | Отсутствующий параметр или некорректная структура XML |
| `E04` | Неверное имя пакета (или не `A-Z` при `test_mode=true`) |
| `E05` | Неверное булево значение (`test_mode`, `ascii_tree`) |
| `E06` | Некорректный URL или путь к тестовому файлу |
| `E07` | Неверный формат версии |
| `E08` | Неверное имя выходного SVG-файла |
| `E09` | Недопустимое значение фильтра |
| `E10` | Дублирование параметра в XML |
| `E11` | Пакет или подходящая версия не найдены в источнике |
| `E12` | Сетевая ошибка или ошибка HTTP при обращении к репозиторию |
| `E13` | Некорректный формат метаданных ответа репозитория |
| `E15` | Синтаксическая ошибка в файле тестового репозитория |

## Демонстрация Этапа 4 на тестовом репозитории

1. **Разветвлённый и ромбовидный граф без фильтра (`examples/config-diamond.xml`):**
   ```bash
   python src/main.py --config examples/config-diamond.xml
   ```
   Вывод (сначала листья `E, G`, затем `D, F`, затем `B, C` и последним корень `A`):
   ```text
   Порядок загрузки зависимостей (корень: A):
     1. E
     2. G
     3. D
     4. F
     5. B
     6. C
     7. A
   ```

2. **Тот же граф с исключением подстроки `B` (`examples/config-test.xml`):**
   ```bash
   python src/main.py --config examples/config-test.xml
   ```
   Вывод:
   ```text
   Порядок загрузки зависимостей (корень: A):
     1. G
     2. D
     3. F
     4. C
     5. A
   ```

3. **Граф с циклами `A -> B -> C -> A` и `D -> D` (`examples/config-cycle.xml`):**
   ```bash
   python src/main.py --config examples/config-cycle.xml
   ```
   Вывод:
   ```text
   Порядок загрузки зависимостей (корень: A):
   Внимание: строгий топологический порядок не существует из-за циклов.
   Заблокированные циклом пакеты: A, B, C, D
   Циклические рёбра: C -> A, D -> D
   Доступны к загрузке до цикла: E
   Приближённый порядок (после разрыва обратных рёбер DFS):
     1. D
     2. E
     3. C
     4. B
     5. A
   ```

4. **Изолированный пакет без зависимостей (`examples/config-isolated.xml`):**
   ```bash
   python src/main.py --config examples/config-isolated.xml
   ```
   Вывод:
   ```text
   Порядок загрузки зависимостей (корень: Z):
     1. Z
   ```
